## 1. 标题
**PlanB：一个能感知约束、重规划行程并分析订单费用影响的 AI 旅行副驾驶**
（PlanB: An AI Travel Copilot with Constraint-Aware Itinerary Replanning and Booking Cost Impact Analysis）
个人项目 · COMP7608

## 2. 问题：为什么普通的 LLM 不够用
- 旅行计划会变：下雨、关闭、延误、延长或缩短行程。
- 让普通 LLM“帮我改一下行程”，它常常会：
  1. 把整个行程重写（丢掉订单和用户在意的安排）；
  2. 违反硬约束（时间重叠、交通时间不够、去已关闭的场馆、改动锁定的项目）；
  3. 漏掉相关联的订单（返程航班、酒店住宿），并且**猜测费用**，或者把已付的钱重复计算。
- 展示一个真实的基线失败案例：即使是 550B 的大模型，对“多待一天”也回答 ¥950，而正确答案是 ¥1,150
  （它漏掉了 ¥200 的改签费）。见 `evaluation/results/nemotron-3-ultra-openrouter-free/raw_outputs.jsonl` 中的 s01。

## 3. 研究问题
“结构化的行程状态 + 确定性约束校验 + 局部修复 + 订单依赖/费用引擎”，能否比“让 LLM 直接修改行程”
更可靠地处理旅行中的变化？

## 4. 提出的方法：架构
用 README 里的架构图：LLM 解析 → 事件 → 影响分析 → 局部修复（束搜索）→ 校验器 →
订单影响 → 费用引擎 → 排序后的方案 → LLM 解释（金额受校验）→ 用户批准。
核心信息：**LLM 负责理解和解释；Python 负责检查和计算；用户负责做决定。**

## 5. 关键设计点
- 未知 ≠ 0：缺少费用信息时，总额就是未知（Story F）。
- 尊重锁定；冲突时返回“无解”，并给出用户可以放宽的选项（Story E）。
- 预览 → 批准 → 提交，带版本号检查；批准永远不会改动真实订单。
- 能用免费/开源模型：只用一次结构化的 LLM 调用来解析，其余都是确定性的。

## 6. 现场演示（约 4 分钟）：`streamlit run app/streamlit_app.py`
0a. 新建行程：示例段落 → 复述（订单锁定，缺价格 → “未知”）→ 可选的一句话更正 → 每日计划（自由用餐时间、想去的地点、按喜好推荐）。
0b. 聊天修改：“我不想去浅草寺了，我更喜欢有历史感的地方” → 3 个已校验的选项（根津神社、六义园、留空）。
1. Story D：“多待一天，12月13日回来” → 只有返程航班被移动；航班和酒店被标记为受影响；
   费用 ¥200 + ¥350 + ¥600 = **¥1,150**；批准 → 版本号变为 2，并提醒用户自行到外部改签。
2. 12/11 上午下雨 → 只有两个户外活动被调整；teamLab 和锁定的晚餐保持不变。
3. 预约冲突 → 无解，并给出“解除寿司晚餐的锁定”这一选项。
备用方案：提前录好屏幕视频，以防网络或电脑出问题。

## 7. 评测设置
- 10 个试点场景（6 种事件类型；包括正常、费用未知和无解的情况），标准答案手工编写。
- 方法：直接问 LLM（A）、加约束提示的 LLM（B）、PlanB、给定正确事件的 PlanB。
- 相同的模型 / temperature / 事实信息 / 输出格式。所有结果由同一个校验器评判。
- 指标：任务成功率、可行性、保留率、订单 F1、费用完全正确率、未知费用处理、无解识别、延迟、token 数。

## 8. 初步结果：两个免费开源模型（真实运行）
10 个试点场景 × 4 种方法，temperature 0。展示 `evaluation/results/model_comparison.png`。

| 方法 | Qwen2.5-3B（本地 CPU） | Nemotron 3 Ultra 550B（OpenRouter 免费） |
|---|---|---|
| 直接问 LLM | 成功 2/10，费用 0/7 | 成功 6/10，费用 3/7 |
| 加约束提示的 LLM | 1/10，费用 0/7 | 8/10，费用 6/7 |
| **PlanB** | **8/10，费用 6/7** | **10/10，费用 7/7** |
| PlanB + 正确事件 | 10/10，费用 7/7 | 10/10，费用 7/7 |

讲解要点：
- **小模型（3B）：基线全面崩溃。** 8 个有解场景一个都没解决，也从不计算费用。
  - 下雨（s03）：把锁定的 18:30 晚餐挪到 14:30，共 9 处硬约束违规。
  - 缩短行程（s09）：第 3 天的活动全部保留。
- **大模型（550B）：基线规划得不错。** 硬约束违规为 0，所有无解场景都识别出来了。
  这一点要坦白承认：强模型在拿到全部信息时，是一个不错的规划者。
- **但大模型在钱上仍然会出错。**
  - s01：回答 ¥950 而不是 ¥1,150，因为漏掉了 ¥200 改签费。
  - 在需要计算改签费的 4 次基线输出中，有 3 次漏掉了改签费。
  - 费用完全正确：直接问 3/7，加约束提示 6/7，PlanB 7/7。
- **PlanB 在不同模型规模下都很稳定。** 引擎是确定性的：两个模型下“PlanB + 正确事件”都是 10/10。
  3B 模型的两次失败都是解析错误（s03 把“下午1点”理解成 12:00；s07 漏掉了延误结束的时间，
  所以 PlanB 选择追问而不是瞎猜）。
- **PlanB 更省。** 每次只调用一次，约 2.5k token，而基线约 14k。用大模型时，PlanB 约 6 秒，基线 54–64 秒。
- **坦白局限。** 这是作者自己编写的小型试点集，相差 1–2 个案例不具有统计显著性。
  评分规则的修正都记录在每次运行的 `NOTES.md` 里。

**新建行程与聊天修改（13 个试点场景，两个模型）：**

| 方法 | 新建：3B | 新建：550B | 修改：3B | 修改：550B |
|---|---|---|---|---|
| 直接问 LLM | 0/8 | 4/8 | 0/5 | 4/5 |
| 加约束提示的 LLM | 0/8 | 8/8 | 0/5 | 5/5 |
| **PlanB** | **2/8** | **8/8** | **4/5** | **5/5** |
| PlanB + 正确请求 | 8/8 | 8/8 | 5/5 | 5/5 |

- 和主评测的规律一样：3B 模型下两个基线 13 个一个都没做对（计划只是碎片、漏航班、违反营业时间）；
  550B 模型下，规则详细的提示词能追上 PlanB。
- 要如实说明：3B 下 PlanB 的新建行程也会下降（2/8）。每一次失败都是读错了请求（最常见的是漏掉返程航班）；
  给正确请求时规划器 8/8、修改引擎 5/5。所以应用在规划之前会先复述理解的内容，让用户一句话更正。
- 用 550B 模型时的成本：PlanB 约 4.6k token、14 秒，基线约 29k token、118 秒。
- 3B 的运行发现了一个规划器 bug（午饭前的推荐景点让赶早班飞机的时间不够），已修复并重新评分，没有任何成功数改变。
  详见两次运行的 `NOTES.md`。

**修正后的论点：** LLM 擅长理解；模型足够强时，也擅长规划。但精确算钱和保证约束成立应该交给代码。
PlanB 让一个免费的小模型也能用。

第 2 页的失败例子用大模型的 s01：解释写得很有说服力，但少算了 ¥200。如果想要更“戏剧化”的例子，用 3B 模型的 s03。

## 9. 局限与 final 之前的计划
- 试点集小，而且是作者自己写的 → 扩展到约 40 个场景，并划分留出集。
- 数据是模拟的，只有一个城市，交通时间是合成的。
- 下一步：更多场景，尤其是费用更复杂的场景（多个订单同时涉及改签费 + 票价差 + 退款）；消融实验
  （去掉局部修复 / 去掉校验器 / 只让 LLM 算费用）；加一个中等规模的 Qwen 作为第三个模型；订单文本抽取；
  时间允许的话做 React 前端。

## 10. 总结
可靠性来自职责分工：语言 → LLM，约束和钱 → 代码，决定 → 用户。

### 答疑准备
- *为什么不让 LLM 自由调用工具？* 免费小模型在多步工具调用上不可靠；受约束的编排器把 LLM 用在它真正有价值的地方，
  并把状态保存在后端（docs/decisions.md D3）。
- *评测是不是偏向你自己的引擎？* 标准答案是根据订单规则手工写的，校验器对所有方法共用，基线拿到的是同样的事实信息，
  基线 B 还额外有一份规则很详细的提示。试点集是开发集；最终数字将来自留出集。
- *费用是“真实”的吗？* 相对于用户提供的规则和报价，它是精确的；PlanB 从不抓取实时价格，并且会明确说明这一点。
- *为什么选这些模型？大模型为什么不用 Qwen？* 预算为零，所以只用免费的开源权重模型。小模型是在本地运行的
  Qwen2.5-3B。大模型是运行当天在 OpenRouter 上实际能调用的、规模最大的免费开源模型：当时免费列表里没有 Qwen，
  Gemma 4 31B 又被上游限流。系统通过 OpenAI 兼容接口调用任何模型，换成 Qwen 只需要改配置，这已列入 final 的计划。
- *用强模型时基线已经很接近了，还需要 PlanB 吗？* 需要，有三个原因：
  - 钱仍然会算错（费用完全正确 3/7 和 6/7，对比 PlanB 的 7/7）。
  - PlanB 的输出是“由结构保证”经过校验的，而不是靠信任。
  - PlanB 用的 token 少约 5 倍，而且 3B 模型也能用。
- *为什么用 3B 模型时 PlanB 新建行程只有 2/8？* 3B 模型读不准带多个订单的长段落，最常见的是漏掉返程航班。
  问题不在规划器（给正确请求时 8/8）。在应用里，用户会看到复述并在规划前更正；这次"一次性"的评测不包含这一步。
  下一步计划用规则抽取器做交叉检查。
