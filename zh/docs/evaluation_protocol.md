# 评测规范（试点阶段，中文版）

> 原文：`docs/evaluation_protocol.md`

## 场景
`evaluation/scenarios/` 里有 10 个试点场景（由 `scripts/build_scenarios.py` 生成）：

| 编号 | 类别 | 预期结果 | 关键检查点 |
|---|---|---|---|
| s01 | 延长行程 | ok | 航班 + 酒店受影响，费用 ¥1,150 |
| s02 | 延长行程 | ok | 缺少航班改签费/报价 → 费用必须是“未知” |
| s03 | 天气变化 | ok | 下雨时段内有 2 个户外活动 |
| s04 | 天气变化 | ok | 1 个户外活动 |
| s05 | 地点关闭 | ok | 博物馆关闭，没有相关订单 |
| s06 | 地点关闭 | ok | 已预订的场馆关闭 → 商家退款 −¥180 |
| s07 | 交通延误 | ok | 当天内连锁调整，保留 teamLab 入场时段 |
| s08 | 预约变更 | 无解 | 被强制改动的时段与锁定的晚餐冲突 |
| s09 | 缩短行程 | ok | 航班改签现金 ¥300，酒店一晚作废 |
| s10 | 地点关闭 | 无解 | 锁定的活动所在地点关闭 |

标准答案的字段：`expected_status`（预期状态）、`affected_booking_ids`（需要旅客采取行动的订单）、
`expected_cost_minor`（预期费用，单位“分”，或用 `cost_unknown` 表示未知）、`must_keep`（仍然可行、应保持不变的活动）。

**报告结果之前，请人工核对标准答案。** 试点集只用于开发；最终数字要来自另外单独构建的留出集（目标 40 个场景）。

## 公平性
所有 LLM 方法使用相同的模型、temperature 0、相同的事实信息（行程、订单及其退改规则和报价、带营业时间的地点目录、
完整的交通时间矩阵、用户请求）、相同的输出格式和费用定义。
PlanB 中的 LLM 只看得到行程/订单/地点的编号，看不到交通矩阵，因为它不需要。

## 成功的定义
- 无解场景：方法回答 `infeasible`（无解）或 `needs_information`（需要更多信息），即它拒绝给出不安全的方案，
  记为 `unsafe_plan_refused`。更严格的 `infeasible_detected` / `status_correct` 只认明确的 `infeasible`；
- 有解场景：状态为 ok **并且** 硬约束违规数为 0 **并且** 保留率 = 1 **并且** 受影响订单集合完全正确
  **并且** 费用正确（误差 ±¥1；若真实费用未知，则应回答 null）。

## 需要说明的局限
试点集很小；数据是模拟的；标准答案由系统作者本人手写；交通时间是合成的；只有一个城市；
结果取决于所用模型及其免费额度是否可用。
