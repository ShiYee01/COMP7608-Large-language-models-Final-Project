# Design decisions

| # | Decision | Why |
|---|---|---|
| D1 | Week-1 front end is **Streamlit**, not React + FastAPI | One person, one week to the proposal presentation. Core logic is a plain Python package, so a FastAPI/React layer can be added later without rewrites. |
| D2 | No database yet: in-memory `TripStore` with revision numbers and history | Approval semantics (base_revision check, re-validation, no double commit) are implemented and tested; persistence is not needed for the demo. |
| D3 | **Constrained orchestrator** instead of a free-form tool-calling loop | The project targets free / small open models. The LLM produces one structured event (validated by Pydantic, retried, rule fallback); the backend calls tools in a fixed order and owns the state machine. No commit tool is exposed to the model. |
| D4 | Any OpenAI-compatible endpoint + response cache | Free providers (Groq, OpenRouter, SiliconFlow) and local servers (Ollama, llama.cpp) all speak this API; caching makes experiments reproducible and saves quota. |
| D5 | Money as integer fen; `None` = unknown | Avoid float errors; unknown fees are never 0 and make the total unknown. |
| D6 | Cost metric = additional out-of-pocket cash from changes to **existing bookings** | Matches Story D (¥1,150). Non-refundable losses are reported separately as non-cash "forfeited". Entry fees of newly suggested activities are not part of the metric. |
| D7 | Repair ranking: disruption → known cost (unknown never cheapest) → travel → preference | Follows PROJECT_CONTEXT §9.4. Removal is weighted higher than replacement, which is higher than a shift; shifts ≤ 30 min count half. |
| D8 | Departure flight is locked but released by an explicit extension/shortening request; a provider-moved reservation is a forced move | The user's own request (or the provider) authorises exactly those changes; all other locks still hold, and conflicts with locks return *infeasible* plus relaxation options. |
| D9 | Ground truth written by hand, not generated by the engine | Avoids circular evaluation. The same validator judges all methods. |
| D10 | Rule-based parser exists for mock mode / fallback only | It was written while looking at the pilot requests, so `planb` results in mock mode are optimistic; real runs use the LLM parser, and the fallback usage is logged in `parse_method`. |
